# Prevent system sleep while running (Settings › General › Power)

## What it is
- A switch, off by default, saved as `piWebPreventSleep: true` in the global `~/.pi/agent/settings.json` (`lib/sleep-inhibit-settings.ts`; off deletes the key, and with no settings file nothing is created; pi's SettingsManager keeps keys it does not know). `GET/PUT /api/sleep-inhibit` answers `{ enabled, supported, unsupportedReason?, active, failure? }` (`SleepInhibitStatus`).
- It works on the machine that runs Pi Web, which is the host that runs the agents, whichever browser asks. The browser holds nothing: no Screen Wake Lock API, no input simulation.
- While at least one session `isRunning()` (the registry `globalThis.__piSessions`, subagent sessions included), one system idle-sleep inhibitor is held; when none runs, or the switch goes off, it is released. Only the automatic idle sleep is blocked: a manual sleep, a closed lid and a shutdown still work, the display may still turn off, and no power plan is changed.
- The page reads the status when Settings opens and after each toggle; it is a snapshot, not a live indicator. The line under the switch speaks only when something is wrong (`sleepInhibitNote()`): the machine cannot hold (switch disabled and shown off, with the reason) or the last attempt failed. A reply's `failure` rides on a 200: only an HTTP error fails the request.

## Moving parts
- `lib/sleep-inhibitor.ts`: one controller on `globalThis.__piSleepInhibitor` (the route and rpc-manager bundles share it). `refresh()` is called from `lib/rpc-manager.ts` wherever "running" can change: every SDK event in `start()`'s subscriber, a prompt's admission and its `finishPrompt()`, a `!` command's start and end, `destroy()`. Add a call at any new place that changes `isRunning()`. `refresh()` is synchronous, never throws and does nothing while the switch is off; the first call reads the saved switch. Never call it from `GET /api/agent/running` or any browser poll: the lock follows the server's own state, not a page's.
- The count is the number of running sessions, so one finishing while others run keeps the hold. Several clients, tabs, reloads and SSE drops change nothing: none of them is an input.
- A 30 s watchdog (`setInterval`, unref'd) exists only while a hold is held or being taken, or after a failure in the current run. It closes the transitions that emit no event (manual compaction exposes idle before `compaction_end`, a failed run start clears its state silently) and ends the "failed in this run" memory when the count reaches 0. With the switch off, or nothing to watch, there is no timer.
- `setEnabled()` (the PUT) saves first, then applies and waits (bounded) for the holder to be ready or gone, so the reply says what is true. Turning off releases at once and leaves every task alone; turning on in the middle of a task takes the hold at once; on with no task holds nothing.
- `lib/sleep-inhibit-adapters.ts` plans one or more "holder commands" per OS. A holder takes the OS lock, prints `ready`, then blocks reading stdin. Releasing closes its stdin and kills it (SIGKILL after a grace period); when Pi Web crashes or is killed the OS closes the pipe and the holder ends by itself, so no cleanup of ours has to run and nothing lingers. The holder's environment is Pi Web's minus `PI_WEB_PASSWORD`.
  - macOS: `/usr/bin/caffeinate -i /bin/sh -c "echo ready; exec cat >/dev/null"`: a `PreventUserIdleSystemSleep` assertion (`pmset -g assertions`). Never `-d`, `-s` or `-u`.
  - Linux: on GNOME `gnome-session-inhibit --inhibit suspend` first (GNOME's idle suspend honors gnome-session inhibitors, not logind idle locks), then `systemd-inhibit` / `elogind-inhibit --what=idle --mode=block` (KDE and the rest). Never `sleep`: it would block a manual suspend. Nothing found: unsupported, saying what to install; systemd is not assumed.
  - Windows: Windows PowerShell runs `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` (0x80000001, written in decimal because PowerShell reads the hex literal as a negative Int32) and then blocks in `[Console]::In.ReadToEnd()`. The state belongs to the calling thread, so that thread has to stay alive as long as the hold: a one-shot call would be undone as its thread ends. No `ES_DISPLAY_REQUIRED`. The return value is not checked (the first call's previous state is not meaningful).
  - Anything else: unsupported, with the platform in the reason.

## Failure
- A failing inhibitor never fails or delays a task: nothing waits for it on the agent path. The reason is logged once (`[pi-web] sleep inhibitor: …`) and kept as `failure`; the switch is never reported `active` unless the holder said `ready` and still runs.
- No retry loop: after a failure (cannot start, no `ready` in 10 s, killed from outside while held) the same run does not try again; the next run, or switching off and on, does. A candidate that fails falls through to the next one of the plan (GNOME's session tool, then logind).
- A hold voided while being taken (the last task ended, the switch went off) is not a failure; its holder is ended.
- `dispose()` (process exit) releases synchronously and stops later `refresh()` calls from taking a new hold while `process.exit` destroys the sessions.

## Tests and what is not verified
- `lib/sleep-inhibit-adapters.test.mjs` (plans for every OS over fake environments), `lib/sleep-inhibitor.test.mjs` (fake holders for the logic, real Node holders for the process lifecycle and a parent killed with SIGKILL, and on macOS the real `caffeinate` checked with `pmset -g assertions`), `lib/rpc-manager-sleep-inhibit.test.mjs` (each hook point), `app/api/sleep-inhibit/route.test.mjs`, `components/settings-ui-helpers.test.mjs` and `components/SettingsPanel.test.mjs`.
- Only macOS has been run against the real OS. The Linux and Windows holders are covered by mocked plans and by the generic process lifecycle, not by a real GNOME, KDE or Windows machine: whether GNOME's `suspend` inhibitor also stops its manual Suspend menu item, whether a given desktop honors the logind idle lock, and a Windows machine whose PowerShell is in constrained language mode (it fails at `Add-Type`, which shows as a failure) are open until someone tries them.

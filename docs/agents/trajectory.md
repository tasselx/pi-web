# Trajectory (the chat's second view)

## What it is and where it sits
- The top bar's `Chat | Trajectory` tab pair (`components/ChatViewTabs.tsx`, rendered first in `renderChatToolbarActions` of `components/AppShell.tsx`) switches the chat area between the conversation and a read-only trajectory view of the same session. It is in place like dsh's view ring: no route, no new tab. The pair is only these two views: the system prompt and the tool definitions are not here but pages of the Session info popover (`SessionInfoPanel`), and that button and its two neighbours, the agent switcher and the branch navigator, belong to the conversation. On desktop `renderSessionBarEnd` draws the three as one group at the top bar's right edge (agents, branches, then Session info; the agents dropdown hangs from the bar's right edge to stay under its button). `renderSessionPanelButtons` and `renderSessionStatsButton` draw nothing while a trajectory is open, the group's wrapper with them, and the file toggle takes over the `margin-left: auto` so it stays on the right edge (two auto margins in the bar would split the free space and push the toggle off it). On a phone the agents and branches buttons keep following the tabs (inside the "more controls" panel when narrow). An effect on `openTrajectorySessionId` closes whichever of their dropdowns (`activeTopPanel`: agents, branches, session) was open, since nothing could close it by its button any more; the tab handler itself never touches that single-slot dropdown. It replaced the old export-HTML button; `GET /api/sessions/[id]/export` stays as it was and is no longer linked.
- Mounting: `ChatWindow` takes `trajectoryView?: ReactNode` and draws it as an `absolute inset-0 z-10` `tabpanel` over the whole chat area, the bottom block under the message area included. The message list and the minimap stay mounted inside a `display: contents` wrapper that gets `visibility: hidden` while the view is open. That keeps the scroll position, the streaming tail-follow and the observers alive, hides the list from the focus order and from assistive tech, and `visibility` inherits through `display: contents`, so no box appears. The minimap's rail is drawn into a slot `ChatWindow` lays over the chat's right edge, outside that wrapper, so the slot takes the same `visibility` itself; the empty spacer the rail leaves in the message row is inside the wrapper. Do not unmount the list to save work: it comes back at the top with its streaming state gone. The panel is a child of the chat root, not of the message area, so it also covers the bottom block (the composer, the extension status bar and its widgets): there is nothing to type into or read there while a trajectory is on screen, and the view runs to the bottom edge, above the safe-area padding. That block takes `visibility: hidden` and keeps its layout. It is not unmounted (the draft and the attachments stay), and it is not `display: none`, which would make the message area taller while the view is open and, on the way back, leave a list that was at the bottom a composer's height short of it. For the same reason the chat's file drop is off while the view is open (`ChatWindow` hands `useDragDrop` `ignoreDrop` instead of `onDrop` and draws no drop overlay; `preventDefault` still runs, so the browser does not open the file): an image would attach to an input nobody sees and go out with the next message. Esc still stops a running agent (see Esc below); it is the one composer control the view keeps. The "scroll to latest" button is not rendered while the view is open.
- z-order: overlay 10, `NoticeShelf` 40, `ExtensionDialog` 90, `ExtensionCustomPanel` 95. An extension asking for input must stay on top of the view, so keep the overlay below them.
- State lives in `AppShell`: `trajectorySessionId` is the session whose view is open (not a boolean), and `openTrajectorySessionId` is that id only while it equals the selected session's. An effect on `selectedSession?.id` clears it, so switching away and back does not reopen a session's trajectory. `handleSelectSession` clears it when a search hit (`entryId`) arrives, even for the session already selected, because the hit scrolls the hidden chat list. The trajectory tab is disabled while no session is selected (a fresh composer).
- Esc: `hooks/useKeyboardShortcuts.ts` stops the running agent on Esc unless the event is `defaultPrevented` or typed into a field. The ledger and the timeline call `preventDefault()` only when Esc closes something of theirs (a selection, a range); with nothing to close they let it through, so Esc still stops a running agent. Keep that rule in any handler added here.
- The view's code loads on first use (script and CSS, two chunks), so the main bundle is unchanged for anyone who never opens it, and a parse problem in an old Safari would hit the view, not the whole page. The entry is `components/trajectory/LazyTrajectoryView.tsx`: a plain component plus a module-level `loadTrajectoryView()`. It is deliberately not `React.lazy` + `Suspense`: a lazy component always suspends on its first render, and react-dom holds the revealed content back until 300 ms after the fallback was committed (`FALLBACK_THROTTLE_MS`), even when the chunk was already loaded. The react-dom that runs is the copy Next vendors (`node_modules/next/dist/compiled/react-dom`, the page loads no other), not the root `react-dom` package; the constant is still 300 in Next 16.4.3, so look there after a Next upgrade. Measured on the same page: 336 ms to the first row with the chunk preloaded through `lazy`, 99 ms without that throttle. Do not go back to `lazy` for this view. A click before the chunk arrives draws an empty overlay for that moment (no fallback text); `AppShell`'s `warmTrajectory` calls `loadTrajectoryView()` when the pointer, focus or a touch reaches the tab, so the chunk is normally in before the click.
- The view is a `memo` component taking only `sessionId` and `running`: `AppShell` re-renders for many reasons (usage, the running set, panels) and none of them should rebuild a list of thousands of rows.
- Layout answers to its own width, not the window's: `.view` is `container-type: inline-size` and the responsive rules are `@container` queries (the stats hide below 720 px, the inspector overlays the list below 800 px). The view sits in a column next to the sidebar and the file panel, so a viewport `@media` would be wrong, and so would `100dvh`. Layout containment makes `.view` the containing block of absolute and fixed descendants: write no `position: fixed` in this CSS.
- This is more than CONTRIBUTING.md's "light web front end" (it is a second view of a session). Keep it in this fork; do not send it upstream as it stands.
- Layout, state machine, timeline, toolbar, search index and the list's look are adapted from `deepseek-ai/deepseek-harness` (`ui-trajectory`, MIT). Every adapted file's header says so and `LICENSE` carries dsh's permission notice. When you port more from there, add the same header and keep that LICENSE section true.

## Data: read-only, never wakes a session, opens from memory
- `hooks/useTrajectoryTranscript.ts` reads `GET /api/sessions/[id]/context` only (`tail=1000` for a first or catch-up page, `tail=200` per poll and per revalidation, `before` for older pages). It never creates an AgentSession and never sends a lease, so opening the view cannot start, keep alive or disturb a session. Do not add either.
- Opening is stale-while-revalidate. A page-memory cache keeps the last 3 sessions' transcripts (valid for 10 minutes after the last successful fetch, at most 6,000 messages each, trimmed from the front with `hasMore` set so the older ones page back in). A view that mounts with an entry paints it in its first frame (`status` starts `ready`) and fetches the newest 200 entries behind it. Hover, keyboard focus or a touch on the tab calls `warmTrajectory` in `AppShell`: it loads the view's chunk and `prefetchTrajectory(sessionId)` puts one `tail=1000` page into the cache (skipped when an entry was fetched in the last 10 s or a prefetch is in flight). The cache lives only in the page's memory, never in `localStorage` or anywhere a reload keeps: transcripts hold file contents and secrets. A reload starts cold. `touchCache()` stamps the entry after a fetch that found nothing new; without it the entry would age by content changes only and an idle session would look expired on every open.
- There is no Refresh button, by design. Freshness comes from the revalidation at open, the 2 s poll while the session runs, one last fetch when it stops, and one fetch when the page becomes visible again after more than 10 s. A background failure keeps the data on screen and shows "Update failed" in the header; only the page that has nothing to show (`status: "error"`) has a button, an inline Retry. Not covered, same as the chat: a writer other than this server (the pi CLI appending to the file) while no wrapper is open for it, and a branch switch made while the view is open: either shows up the next time the view opens.
- The running flag is a parameter: `useTrajectoryTranscript(sessionId, running)`. `AppShell` passes `runningSessionIds.has(id)`, the set the sidebar already polls from `/api/agent/running` every 2.5 s, so the view does not poll it again. The "Running" badge and the first poll therefore lag a run's start by up to 2.5 s, and the final fetch lags its stop the same way.
- The context route has two sources: a live wrapper's in-memory `SessionManager`, else the file through `openSessionManager()`. While a wrapper exists, entries written to the file by anyone else (the pi CLI) are not seen until the wrapper goes. That is right in production, where the wrapper is the only writer, and a trap for tests: selecting a session in the page warms its wrapper, so a file appended to afterwards looks stale. Use `PI_CODING_AGENT_DIR` with a temp dir, never the real sessions. To get a running session with no model call, send `{ "type": "bash", "command": "echo x; sleep 8" }` to `POST /api/agent/[id]` (or `!echo x; sleep 8` from the composer): a bash run counts as running (`isBashRunning`) and appends one bash row when it ends.
- Only completed entries exist: an assistant message appears when it ends, so while the model is generating nothing in the list shows it. The header's "Running" badge covers that gap.
- Polling runs only while `running` and the page is visible; running turning true starts it, so the view may be opened before a run begins. The running→idle edge makes one last `tail=200` fetch so entries written just before the stop are not lost. One request is in flight at a time; a request that arrives meanwhile is queued and run after it, and the queue loop re-reads the current `AbortController` each round because dev-mode effects clean up and rerun.
- Poll pages merge with `mergeTailPage()`, older pages with `prependOlderPage()` (`components/subagent-viewer-state.ts`, shared with the subagent viewer). `mergeTailPage()` keeps what is loaded when the page overlaps it and replaces the whole transcript when it does not; `prependOlderPage()` drops an older page whose cursor is no longer the oldest loaded entry. The hook returns the current transcript object when a merge changed nothing (`sameTranscript()`: entries are append-only, so the same count and the same first and last ids mean the same content). Keep that bail-out: every new object re-runs the derivation over the whole transcript, and a running session would do that every 2 s for nothing.
- Away from the page: polling pauses while the tab is hidden, so more than one poll's worth of entries can pile up unseen, and the next `tail=200` page would not overlap what is loaded: the history on screen would be swapped for the newest 200. When the last successful fetch is more than 10 s old, a `tail=200` request therefore asks for a full page (`tail=1000`) instead, which reconnects to what is loaded. The same rule makes a cold open (no fetch yet) ask for a full page, and a reopen after more than 10 s revalidate with one.
- It shows the session's active branch (default leaf) only. `tail` counts visible entries (user and assistant messages, compaction dividers), not tool results, so `tail=1000` is up to 1000 of those with their tool results (the route caps the raw window at `tail * 6`). Turn numbers count from the first loaded turn: they renumber when older pages load, or when a page that does not overlap replaces the transcript.

## Deriving records (`lib/trajectory/derive.ts`)
- A user message opens a turn. Each assistant message starts a step group: its own cell, then one tool cell per tool call with the matching result merged in by `toolCallId`. A record id is the entry id, or `${assistantEntryId}:${toolCallId}` for a tool cell, so selection survives re-reads and merges.
- A tool call's span starts at `result.timestamp - result.durationMs` (the result's timestamp is its end). An assistant's starts at its own `timestamp` (request start) and lasts `durationMs`.
- A call without a result is `running` while the session runs (`live`) and `interrupted` ("No result") otherwise, so a stopped or crashed session never shows a spinner forever. A tool result with `isError` is an error row; so is an assistant that ended with `stopReason` `error` or `aborted`, whose `errorMessage` is its text when it has none.
- `compaction` custom messages become a `compacted` cell; other `custom` ones a `context` cell; `bashExecution` a tool cell. Roles the derivation does not know, such as the persisted `system` messages (provider input, see sessions.md), fall through the `switch` and are skipped, never an error.
- pi records no time to first token, so the inspector shows an average output speed (output tokens over total duration) with a hint saying so. Do not label it a generation speed or TTFT.

## Search, collapse and the timeline (semantics of dsh's view)
- Search filters the list and bypasses collapsing: a match is never hidden inside a collapsed turn or step. The index (`lib/trajectory/search-index.ts`) is incremental by record id so a poll only indexes what changed.
- Collapse applies turns first, then step calls, each skipped when its set is empty. The toolbar buttons toggle all of them; a row's own button toggles that step only (`ledger.*` labels).
- A timeline drag selects a range that emphasizes the rows inside it and dims the rest, scrolling to the first; it does not filter. Selecting a row outside the range clears the range; a timeline span click clears the range, selects and scrolls; a click on empty timeline only scrolls. The Duration toggle clears the range.
- The timeline, the header stats, search and collapse work on every loaded record, not only the rows the list has mounted.

## The list (`components/trajectory/TrajectoryLedger.tsx`)
- Rows are a fixed 30 px (turn header 26, group header 22, summary row 22; the heights are fixed in `TrajectoryLedger.module.css`). The list is windowed, not virtualized: it mounts the last `INITIAL_ROWS` (120) rows and reveals older resident ones in batches of `REVEAL_ROWS` (200) when the reader scrolls within `REVEAL_NEAR_PX` (400) of the top or presses "Load earlier trajectory". Only when no resident row is left does that button ask the server for an older page (`onLoadEarlier`); the ledger raises the window before the request so 200 rows of the new page mount when it lands. Mounting all of a long session's rows is what made opening slow: on a page of 1,942 records (1,000 entries, 3.4 MB) it was 24k DOM nodes and 0.7-0.8 s to the first row in dev (React render 158 ms, commit 171 ms of which 167 ms was forced layout, about 390 ms of style, layout and paint).
- The window is a pin and a count (`LedgerWindow` in `lib/trajectory/ledger.ts`): `pin` is the row key (`recordRowKey()`: record id plus the collapsed-summary kind) of the first mounted row and `extendUp` how many resident rows above it are mounted too; `resolveLedgerWindow()` turns that into the start index. A key, not an index, so a poll appending rows or a page prepending older ones changes nothing that is mounted. A pin that search or collapse filtered out falls back to the last 120 rows and re-pins; the component does that as a render-phase `setState`. `extendUp` only grows.
- A window that starts in the middle of a turn gets a turn header forced onto its first row, because the real one is above the window and unmounted; without it the sticky header has nothing to stick to and the reader cannot tell which turn the rows belong to.
- Reveal keeps the reader's place: the anchor is the distance from the bottom of the scroller (`olderAnchorRef`), restored in a layout effect keyed on `[records, start]`. Row numbers (`#n`) count from the first loaded record, so they shift when an older page loads: anchor on a record id or a distance, never on the number.
- `scrollToRecord(index, block)` is the one way to bring a record into view: mounted, it scrolls; unmounted, the window grows to include it and the scroll finishes in a layout effect on `[start]` (`pendingScrollRef`). Arrow keys, Home, End and the timeline's `scrollRequest` use it. A far jump (Home, a timeline click on the first record) mounts everything in between: about 0.5 s for 1,942 rows. That is a deliberate trade for a window with no placeholders.
- The ledger remounts when search turns on or off (`key={searchMatchIndexes === null ? "all" : "matches"}` in `TrajectoryView`), so the window starts over. Without it a search that matches one early row leaves the pin on that row and clearing the search mounts every row after it (1,740 here). A remount must not replay an old `scrollRequest`: the handled marker starts as the request already present at mount.
- Turn headers are sticky, so every record renders as a `Fragment` of direct children of the scroll container. A wrapper `div` per record would end each header's stickiness at its own record.
- Follow tail: while the list is within `FOLLOW_TAIL_PX` (48) of the bottom, new records scroll into view; once the reader scrolls up it leaves the position alone.
- The view reaches the window's bottom edge, so the ledger ends with 2 px of `padding-bottom` and the same `scroll-padding-bottom`, which keeps that gap when ↑ ↓ or `scrollIntoView("nearest")` land on the last row. It is deliberately tiny ("a little gap": 24 px, the inspector body's own bottom padding, then 12, 8 and 4 px were tried and judged too much). The padding is inside `scrollHeight`, so the follow-tail and anchor distances, all measured from the scroller's end, do not change (2 px is well inside `FOLLOW_TAIL_PX`). Without it the last row sits flush against the window's edge.
- A tool call still running shows a pulsing dot in the time column (the same look as the header badge, still under `prefers-reduced-motion`); an interrupted one shows only in the inspector.
- A row's hover tip (the native `title` on the summary) is the whole text, never the cut summary. `cell.text` stops at 200 characters with "…" so derivation need not scan a multi-MB body; `fullCellText()` in `lib/trajectory/derive.ts` returns the untruncated one (user / assistant text, the tool's primary argument, a `!` command) and only when the summary ends in "…". It runs at render and not in `deriveTrajectoryLayout`, which re-runs on every poll and does no heavy work. Chromium clamps any native tip at 1,024 characters (Firefox 3,250), so a longer text is cut by the browser itself, without a "…"; the inspector holds all of it. Keep `fullCellText()` in step with the `text` each `*Cell()` builds.
- Clicking a row selects it unless text is selected in it (so copying works); a click on the list's empty area clears the selection; Escape clears it too (and is consumed only then, see Esc above). Arrow keys, Home and End move it.
- Measured in dev on the 1,942-record page, locally: click to first row 150 ms with nothing preloaded (the chunk, a 32 ms page fetch and one frame of about 96 ms), 99 ms after a hover warm-up, 66-77 ms reopening from the cache; mounted panel 3.4k DOM nodes instead of 24k. A first-ever open in dev also pays about 300 ms for Turbopack to compile the chunk; production does not. With every row mounted (after Home, or after revealing everything) scrolling holds 60 fps, opening the inspector costs about 150 ms and closing it about 90 ms, and the worst interaction (expand all, clear a search without the remount above) stalls the main thread about 0.4 s. If sessions of tens of thousands of records matter, virtualize the rows; the sticky headers and the anchor above have to survive that.

## Strings and styling
- All strings are `trajectory.*` keys in `en`, `zh-CN` and `zh-TW`, except the tab pair's own `chatView.*` keys (`chatView.chat`, `chatView.trajectory`, `chatView.trajectoryUnavailable`, `chatView.tabsLabel`). The adapted modules call unprefixed keys through a translator (`tt` in `TrajectoryView.tsx` prepends `trajectory.`). Plurals are explicit `.one` / `.other` keys chosen in code, not ICU. `trajectory.state.retry` is the error page's button; there is no refresh string. `app/page.tsx` already wraps `AppShell` in `I18nProvider`, so the view brings none.
- Colors are theme tokens (`--bg`, `--bg-panel`, `--border`, `--accent`, `--text*`). The one literal is the error red `#ef4444`, which `MessageView` also uses. dsh's own tokens (`--dsw-alias-*`) must not come along when porting.
- The tab pair copies the top bar's button look (36 px, `border-top: 2px solid var(--accent)` and `--bg-selected` when selected) and the Sessions | Files tablist's keys (roving `tabIndex`, ←/→/Home/End move and focus). On a narrow phone (≤ 480 px) it is icon-only inside the "more controls" panel with the other toolbar actions; choosing a tab leaves that panel open, like the other actions there.
